# Backend (502-backend)

Loaded when working under `502-backend/`; the root `CLAUDE.md` has the product, roles, resource rules and environment.

## Commands

```bash
npm run test:e2e           # test/{foundation,reports,costing,board,pr,approvals,live,einvoice,report-site}.e2e-spec.ts --runInBand; resets the DB in test/e2e.env (karaoke_test)
node test/load/bench.mjs load <from> <to>  # load test (10 cashiers + 10 report downloads, STAFF=n floor-staff phones) on test/load/generate.sql data; setup in docs/resource-rules.md §6
npx ts-node test/fake-minvoice.ts 4555  # fake Minvoice for trying e-invoices in a browser: run the backend with MINVOICE_URL_TEMPLATE=http://127.0.0.1:4555/{taxCode} (not in production); the script prints the password its fake accepts
npx prisma db seed         # branches cs1–cs5 + admin and the default accounts (password 12345678), cs5 rooms and menu; re-running only adds missing seed entries (matched by name); SEED_DEMO=1 adds demo accounts, rooms and products for cs1/cs2; details in prisma/seed.ts
```
`npm run build` puts the output in `dist/src/main.js` (`prisma/seed.ts` is inside the TS root). Migrations (`prisma/migrations`, each described in root `DEPLOYMENT.md` §6): `0_init` is the baseline of the legacy `db push` schema and `20260926000000_foundation` is hand-written and migrates legacy rows. `test/fixtures/legacy-data.sql` is legacy-shaped data for rehearsing them. Don't use `prisma db push` any more. `prisma migrate dev` needs a TTY; elsewhere write the SQL with `npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url <db> --script`.

Prisma reads `502-backend/.env` itself (before Nest's ConfigModule), so to run against another database pass `DATABASE_URL=... npm run start:dev` in the shell.

The e2e database is the disposable `kara502-pg` container (port 5433, see the comment in `test/e2e.env`); start it with `docker start kara502-pg` first. If a unit test fails with `Cannot convert undefined or null to object` at an `@IsEnum(...)` of a Prisma enum, the generated client is stale: run `npx prisma generate`. Run the e2e suites one at a time and not under heavy load: they drive real transactions (the edit/checkout race test) and a machine running out of resources made them fail spuriously, while 16 later runs passed.

Connections: `DATABASE_URL` carries `connection_limit=10&pool_timeout=20`; `PrismaService` lets a transaction wait 10 s for a connection (`transactionOptions.maxWait`, Prisma default 2 s); reports use a second client, `ReportPrismaService`, on the same URL with `connection_limit=3&pool_timeout=50`.

## Architecture

- All routes are under `/api`; Swagger at `/api/docs`. CORS reflects any origin with credentials. `src/app.setup.ts` (`configureApp`) wires the prefix, cookie parser, a global `ValidationPipe` (whitelist + transform, Vietnamese messages) and `PrismaExceptionFilter` (P2002/P2003 → 409, P2025 → 404, P2024/P2028 — no free connection or transaction out of time — → 503 "Hệ thống đang bận"); it is shared by `main.ts` and the e2e tests.
- One Nest module per resource: `auth`, `users`, `branches`, `rooms`, `categories`, `products`, `orders`, `inventory`, `funds`, plus a global `common` module.
- **Auth**: `JwtAuthGuard` and `RolesGuard` are global `APP_GUARD`s — every route requires a valid access token unless marked `@Public()`, and `@Roles(...)` restricts by role (`MANAGERS`, `SALES`, `ALL_ROLES` in `src/auth/roles.ts`). The JWT strategy reloads the user from the DB on every request (`AuthUser`, `@CurrentUser()`), so role/branch changes and locking (`active=false`) take effect immediately. `POST /auth/login` returns a 15-min access token and `sessionExpiresAt`, and sets the `Refresh` httpOnly cookie. A session lasts **24 hours from login** (`SESSION_TTL_SECONDS` in `config/env.ts`), not extended by use: `POST /auth/refresh` re-issues only the access token, never valid past the session end. The refresh token carries `pwd`, an HMAC stamp of the password hash, so changing/resetting a password ends every earlier session (`change-password` hands the caller a new one); tokens without it are rejected. `LoginThrottle` (in memory) locks a username for 15 min after 5 wrong passwords in 15 min (429); unknown usernames are compared against a dummy hash. `configureApp` adds `helmet`; CORS allows `CORS_ORIGINS` (unset: any origin in dev, none in production) and Swagger is off in production unless `SWAGGER_ENABLED=true`. Security review and remaining risks: `docs/security-review.md`.
- **Branch scoping** (`common/branch-scope.service.ts`): endpoints take an optional `?branch=<code>`. Only the chain manager's value is honoured; everyone else is always scoped to `user.branchId` and gets 403 for another branch's code or record (`assertBranchAccess`). Never trust the URL branch for anything else.
- **Per-branch data**: `Branch` model; `Category`, `Product`, `Room`, `Order`, `FundTransaction`, `StockDocument`, `StockMovement`, `DiscountRequest` (a cashier's request to change discounts/VAT, with its decision) and `OrderEvent` (the log of time unlocks, `TIME_UNLOCK`; the log of discount/VAT changes is `DiscountRequest`) all have `branchId`. Each branch has its own catalog and stock.
- **Orders / billing**: a room session is an `Order` with `status=PENDING`. `POST /orders {roomId, cskhId?, serverId?}` opens it, snapshots the room's `pricePerHour` onto the order (with `taxPercent` defaulting to 10) and sets the room `ACTIVE` in one transaction. New rooms are `VIP` unless a type is given. `PATCH /orders/:id {items: [{productId, quantity}], cskhId?, serverId?}` replaces the items (it no longer takes discount or VAT fields, see Discounts below; the phục vụ of the session may send `items` only); prices come from the server (existing lines keep their snapshot price). `billing.ts` `computeBill` is the single billing formula: room fee = started minutes/60 **rounded to 0.01 hour** (`billedHours`, 83 min = 1.38 h) × the order's price, to the đồng (no 1,000 rounding); each discount has a percent and an amount — a percent > 0 is applied to the live base (products / room fee) and wins, otherwise the amount is a fixed sum; discounts are capped at what they discount; tax = `taxPercent` of room fee + products after discounts. Percent amounts and tax are rounded **up to the đồng** (`roundUpToDong`), never to 1,000. There is no service fee any more: `serviceFeePercent/Amount` stay in the schema for old bills but are not accepted by the API, and every (re)computed bill sets them to 0. Order responses (`orderInclude`) carry only `{id, name, unit}` of each line's product and `{id, name, type}` of the room (`Pick<>` in the frontend `lib/types.ts`). `GET /orders/:id/preview` shows it live, `POST /orders/:id/checkout {paymentMethod}` persists the applied amounts, frees the room, writes `SALE` stock movements and the fund receipt in one transaction. Each bill line keeps `OrderItem.unitCost`: the cost per unit of what the bill took from stock (Σ value / Σ quantity of its movements; 0 without stock tracking), set at checkout and after every correction (`snapshotItemCosts`); voiding or correcting puts goods back at that cost. Every writer of an order (`update`, `checkout`, `cancel`, `void`) first locks the row via `lockOrder` (conditional `updateMany`), so an item edit and a checkout never interleave; stock rows are always locked in product-id order. `POST /orders/:id/cancel` (managers) drops an open session (and expires its pending discount request); `POST /orders/:id/void {reason}` (`CHAIN_ONLY`) voids a paid bill: `REVERSAL` movements put back the net quantity the bill took and the fund receipt is cancelled. `PATCH /orders/:id/paid {reason, items?, adjustments?, cskhId?, serverId?, startTime?, endTime?, pricePerHour?, paymentMethod?}` (`CHAIN_ONLY`) corrects a paid bill: it is recomputed (the charged room fee is kept unless times/price change), the stock difference is written as `SALE`/`REVERSAL` movements, and the fund receipt takes the new amount, method and payment time (bills paid before receipts existed stay without one); frontend `components/sales/edit-paid-bill-dialog.tsx` from the bill sheet. **Time lock** (chốt giờ): `POST /orders/:id/lock-time` (`SALES` and the session's phục vụ) sets `Order.timeLockedAt/timeLockedById` under `lockOrder` (409 when already locked) and closes the open PR visits at that moment; from then `billOf` (`orders/bill-of.ts`, with `adjustmentsOf` and `billedEndOf`) bills the room fee up to `timeLockedAt` instead of now, in `GET /orders/:id/preview` and at checkout, and **checkout writes `endTime = timeLockedAt`** (so the bill's duration, business day, bill number, fund receipt time and reports all share that moment; cancelling an open session still ends at now). The `SALE` stock movements of that checkout carry the checkout time, not `timeLockedAt`, so for a bill locked before 06:00 and paid after it, Nhập – xuất – tồn may place the sale one business day after revenue/profit. Ordering items and sending discounts stay possible after the lock; no PR can be added, and a PR visit's times are capped at the lock (`pr-session-rules.ts`). `POST /orders/:id/unlock-time` (`SALES`, 409 when not locked) clears the lock and writes an `OrderEvent(TIME_UNLOCK, lockedAt)` in the same transaction (the clock then runs on from the start; closed PR visits are not re-opened). The room map (`activeOrder.timeLockedAt`) shows the room as locked. **Discounts** (`src/discounts`, `DiscountsModule`): discounts and VAT of an open session change only through `POST /orders/:id/adjustments {discountPercent?, discountAmount?, hourlyDiscountPercent?, hourlyDiscountAmount?, taxPercent?, note?}` (`SALES`). Every change is written as a `DiscountRequest` row, which is both the approval queue and the audit log (`source` `REQUEST`/`DIRECT`/`PAID_EDIT`, `status` `PENDING`/`APPROVED`/`REJECTED`/`CANCELLED`/`EXPIRED`; `before`/`after` are JSON with exactly the five keys above plus the bill total before/after). `discount-rules.ts` `needsApproval(before, after)` is true when any discount grows, a percent falls to 0 over an amount > 0 (billing ignores an amount while its percent is > 0, so the amount becomes the discount) or `taxPercent` falls (field by field, not by total, because percents follow the live bill); `adjust` stores `after` through `normalizeAdjustments` (a percent > 0 sets its amount to 0, and the bill panel does the same when a percent is typed), so no amount waits unseen behind a percent; a manager's change, or a cashier's change that needs no approval, is applied at once and logged as a `DIRECT` row; a cashier's change that needs approval must carry a `note` and creates a `PENDING` request instead, with one pending request per order (checked under the order lock; a second one is 409) and **checkout answers 409 while a request is pending** (`assertNoPendingRequest`). Cancelling the session expires its pending request (`expirePendingRequests`); `editPaid` logs a `PAID_EDIT` row when it changes discounts or VAT. `GET /discount-requests/pending` (the queue, oldest first, cap 200, `X-Total-Count`) and `/pending-count` (the sidebar badge) serve the managers — a branch manager sees their branch, the chain manager every branch (`branchId IN (all ids)` so the `(branchId, status)` index serves it); `GET /discount-requests?from&to&branch&status` is the log (cap 500, `X-Total-Count`, `READERS` incl. BOARD, by business day), `GET /discount-requests/:id` one row, and `POST /discount-requests/:id/approve|reject` (`MANAGERS`, `note` on a rejection) and `/cancel` (`SALES`) decide it under the order lock: **whoever acts first wins**, the next one gets 409 naming who decided and when (`decided-message.ts`). Approving applies the `after` values to the order; a request whose bill changed meanwhile (its `before` no longer matches) or that waits on a closed session is set to `EXPIRED` and the approver gets 409. Rejecting needs a `note`. The ledger helpers used inside other transactions are in `orders/discount-ledger.ts`. The frontend mirrors `computeBill` in `lib/billing.ts` for the live total — keep them in sync.
- **Live events** (`src/live`, `LiveModule` global): a signal-only WebSocket at `/api/ws` on the same HTTP server (`@nestjs/platform-ws`, `WsAdapter` set in `configureApp`), for the cashier and manager screens; floor staff keep polling. A client sends `{type:"auth", token}` within 5 s (never the token on the URL; `maxPayload` 4 KB, anything but `auth` is ignored); `LiveGateway` verifies it like `JwtStrategy` (signature, expiry, user reloaded from the DB, `SALES` roles only), answers `{type:"ready"}`, pings every 30 s (Cloudflare drops silent connections at ~100 s) and closes after two missed pongs, when the token is 60 s past its expiry without a new `auth` (4002; checked in the 30 s tick, so the close lands 60–90 s after `exp`), on a bad auth or a failed lookup (4001) or over capacity (1013: `LiveRegistry` caps 100 sockets, 5 per user and `MAX_PENDING_SOCKETS` 20 for sockets that have not authenticated, each of which holds a slot for at most 5 s). One socket has at most one `auth` lookup in flight (further `auth` frames are dropped meanwhile, as are frames on a socket no longer OPEN); a socket that never authenticated is closed at its first refused `auth`; a signed-in one survives up to 3 badly signed tokens (`failedAuths`, `jwt.verify` failures only) but is closed at once (4001) when the account lookup refuses it (inactive or not a `SALES` role). Events carry ids only: `room.changed {branchId, roomId}` and `order.changed {branchId, orderId}` go to the branch's sockets, `discount.requested {branchId, requestId}` to the branch's managers, `discount.decided {branchId, orderId, requestId, status}` to the branch; chain managers get everything. Services call `LiveEventsService.roomChanged/orderChanged/discountRequested/discountDecided` **after** `$transaction` resolved, never inside it (`OrdersService` create/update/checkout/cancel/lockTime/unlockTime, `DiscountsService` adjust/decide — also `EXPIRED` from a stale decision —, `OrdersService.cancel` (`discount.decided … EXPIRED` for the pending request the cancel expires, ids from `expirePendingRequests`), `PrSessionsService` add/end/update/remove). Nothing per message is logged. e2e: `test/live.e2e-spec.ts`.
- **Số hóa đơn** (`orders/bill-number.ts`): closing a bill — checkout or cancelling an open session — gives it `billNumber` = DDMM of the business day + 4-digit room code (last number in the room name, right-padded with 0: P401 → 4010) + the day's sequence in the branch (3+ digits), e.g. `27093020001`; voiding keeps it and numbers are never reused. `BillCounter (branchId, businessDate)` hands out the sequence with one atomic `INSERT … ON CONFLICT … RETURNING` inside the closing transaction (always taken right after `lockOrder`); a bill thêm tay of the report site takes its number from the same counter (`nextBillNumberOn`, which `nextBillNumber` wraps), so the main site's sequence of that day skips it. `GET /orders` returns the newest 1000 bills with the match count in `X-Total-Count`; the Hóa đơn page takes its totals from `GET /orders/summary` (same filters, `{billCount, paidCount, cancelledCount, collected, vat}`, summed in SQL on the report pool), never from the list. `GET /orders?billNumber=<digits>` searches by number prefix over every day, as a `gte/lt` range so the `(branchId, billNumber)` index serves it; the frontend shows `billLabel(order)` (number, or `#id` for an open session).
- **Business day** D = [D 06:00, D+1 06:00) in server local time (venue hours 11:30 → 06:00), so every moment belongs to exactly one day (`common/dates.ts`: `getBusinessDayRange`, `businessDayRange(from, to)`, `businessDateOf`). All reports use it: `GET /orders?from&to` / `?businessDate=` and `GET /reports/*` (by **payment time** `endTime`), funds, stock documents and movements. The frontend defaults its date filters to `businessDate()` (`lib/format.ts`), not the calendar date.
- **Inventory**: `Product.stockQuantity` changes only through `InventoryService.applyMovement` (atomic increment + one `StockMovement` ledger row with `balanceAfter`), so it always equals the sum of its ledger. `GET /inventory/documents` (newest 200) and `GET /inventory/movements` (newest 500) send `X-Total-Count`; the Phiếu kho page takes its import/export totals from `GET /inventory/documents/summary`. Phiếu nhập/xuất = `POST /inventory/documents {type, lines, paymentMethod?}`, codes like `PN-CS1-20260926-0001`; `costPrice` is the **weighted average cost**: `applyMovement` values every movement with `inventory/costing.ts` (`costMovement`: goods in at their cost — an import's line cost, goods put back at the cost they left at — move the average with `receive`; a cancelled import comes out with `unreceive`; sales and exports leave at the average) and writes `StockMovement.unitCost` and `costAfter` under the same row lock; nothing else writes `costPrice`; an import with `paymentMethod` also writes its phiếu chi; exports cannot go below zero, sales may. `POST /inventory/documents/:id/cancel {reason}` reverses each line at the cost it moved at and cancels the linked phiếu chi. `trackStock=false` products (phụ thu, dịch vụ) are never deducted, and tracking cannot be turned off while stock remains. `GET /inventory/stock` and `GET /products` include `pendingQuantity` (ordered in open sessions, deducted at checkout); stock also lists discontinued products that still hold stock.
- **Funds**: `FundTransaction` (INCOME/EXPENSE, `method` CASH/TRANSFER). Checkout writes the receipt of a bill (`orderId`), a paid import its payment (`stockDocumentId`) — helpers in `funds/fund-ledger.ts`, called inside the source's transaction. `GET /funds` returns the newest 500 entries with the match count in `X-Total-Count` (the page and its Excel export warn when entries are left out). Manual entries via `POST /funds`; their `category` is one of the fixed list in `funds/fund-categories.ts` (chi: Lương, Mặt bằng, Điện nước, Sửa chữa – bảo trì, Marketing, Vật tư tiêu hao, Thuế – phí, Khác; thu: Thu khác; default Khác / Thu khác; older free-text categories count as Khác in the profit report); `POST /funds/:id/cancel {reason}` cancels manual entries only (linked ones follow their source). Cancelled entries (and bills/documents: `cancelledAt/cancelledBy/cancelReason`) stay visible but leave every total. `GET /funds/summary` returns opening/closing balance, income/expense (with `salesIncome`/`purchaseExpense`) and a per-method split; `salesIncome` for a period equals `collected` of `GET /reports/revenue` for the same period, and `salesVat` equals its `vat`.
- **Reports** (`src/reports`, managers and BOARD; `GET /reports/revenue` also the cashier): every report service queries through `ReportPrismaService` (`prisma/report-prisma.service.ts`, a read-only client with its own 3-connection pool, so report downloads queue among themselves and never take the cashiers' connections), and `ReportsController` plus `GET /funds/summary` (whose sums also run on that pool) carry `SharedRequestInterceptor` (`common/shared-request.interceptor.ts`: identical requests in flight — same path, sorted query and branch scope — share one computation; nothing is kept once it ends). **Revenue is always before VAT** — `revenue` = Σ(`finalAmount` − `taxAmount`), `vat` = Σ `taxAmount`, `collected` = Σ `finalAmount` (= the fund's `salesIncome`; `GET /funds/summary` also returns `salesVat`). `report-sql.ts` holds the `$queryRaw` pieces: `businessDateSql` (UTC column → the process's time zone − 6 h, the same day as `businessDateOf`), `paidOrdersWhere`, `REVENUE_COLUMNS`. The SQL groups by business day (and a dimension); `buckets.ts` rolls days into day/week (ISO)/month/quarter/year periods and gives the `previousRange` ("so với kỳ trước" of the revenue and branch reports, by `groupBy`: day → the same number of days right before; week/month/quarter → as many **whole** periods right before, e.g. 01/09–27/09 by month → all of August; year → the same dates a year earlier), and `revenue-metrics.ts` turns sums into metrics — both pure and unit-tested. Queries are `ReportQuery {branch?, from, to, groupBy?, compare?}`, ranges up to `MAX_REPORT_RANGE_DAYS` (1830). Scope goes through `resolveOptionalBranchId`: the chain manager without `branch` gets the whole chain (plus `byBranch`). `GET /reports/{staff?role=cskh|server|cashier, rooms?by=room|type, products?by=product|category, hours}` (`breakdown-reports.service.ts`) break the same bills down by subject, and their rows always add up to the revenue report: rows without a subject (id null: Chưa gán, Không phòng, Không danh mục) come last. Staff: each bill counts in full for its CSKH, server and cashier (`checkedOutById`). Rooms list every room of the scope, with occupancy = room minutes / (days × `VENUE_OPEN_MINUTES` 1110 × rooms). Products spread a bill's product discount over its lines in SQL, then `roundToTotal` rounds to the đồng without losing any; queries joining `OrderItem` never use `REVENUE_COLUMNS`. Hours: ISO weekday of the business day × local hour of `startTime`. `GET /reports/branches` (chain manager only) and the revenue report share one day × branch query. The pure helpers are in `breakdowns.ts`; `report-scope.ts` resolves the branch and checks the range.
  `GET /reports/profit` (`accounting-reports.service.ts`, pure sums in `profit.ts`) is the P&L per period (`groupBy`, no comparison): revenue before VAT − cost of goods sold (Σ quantity × `OrderItem.unitCost`) = gross profit, − manual phiếu chi by category − exports of documents still standing (hao hụt) + manual phiếu thu = profit; VAT and the imports' amounts are shown apart. `GET /reports/inventory` is nhập – xuất – tồn per product: opening/closing = balance × `costAfter` of the last movement before the range / its end (one `LATERAL … ORDER BY createdAt DESC, id DESC LIMIT 1` index lookup per product — Prisma stamps `createdAt` after `applyMovement` locked the product row, so per product it follows the writing order), flows = Σ quantity × `unitCost` by type (imports, sales, exports positive; reversals and adjustments signed), so values may differ from the closing by the rounding of the average. Each row also carries `averageCost` (đơn giá bình quân: the cost after the last movement before the range's end, the closing balance's cost). Rows also carry `stockIn` / `stockOut`, the net nhập / xuất of the ledger (the movements are grouped by type and sign: a reversal out undoes an import and comes off `stockIn`, a reversal in puts back what a bill or an export took and comes off `stockOut`), so opening + stockIn − stockOut = closing in quantity. The page and its Excel sheet show Tên mặt hàng, ĐVT, Đơn giá bình quân, then Tồn đầu / Nhập / Xuất / Tồn cuối, each as SL + Thành tiền (the sheet gets two header rows from `ExportColumn.group` in `lib/excel-export.ts`; the total row sums only the amounts); the Xuất tile splits it into bán and phiếu xuất. The products report adds `cost`, `grossProfit` and `margin`. `report-sql.ts` also has `periodWhere`/`branchWhere` for any dated table.
- **Excel import** (`src/imports`, managers only): the browser reads the file and maps its columns, then posts JSON rows (`{row, ...fields}`, max 1000; `app.setup.ts` mounts a 5mb JSON parser on `/api/imports` only, every other route takes 1mb) to `POST /imports/{categories,products,rooms,users,stock-import}`. `dryRun: true` only returns each row's verdict (`CREATE`/`UPDATE`/`SKIP`/`ERROR` + Vietnamese message); otherwise the rows are checked again and written in **one transaction**, or nothing when any row is an error (400 with `rows`). Records match by name within the branch (case/space-insensitive, diacritics kept — `import-utils.ts` `normalizeName`), accounts by username (or full name); `onDuplicate` SKIP/UPDATE decides what happens to matches, and UPDATE only writes the mapped, non-empty fields. Products/categories/rooms reuse the rules of their services; accounts are created without a password (username generated from the name when missing) and roles go through `UsersService.checkAssignment`; a stock sheet becomes one phiếu nhập via `InventoryService.writeDocument` (the transaction body of `createDocument`), merging repeated products at the weighted average cost and optionally creating missing products.
- **PR/KTV** (`src/pr`, routes `/pr/staff`, `/pr/attendance`): `PrStaff` is a branch's list of PR/KTV (not accounts: name, optional code unique per branch, phone, note, `active`); `PrAttendance` is the roll call, one row per person per business day (`@@unique([prStaffId, businessDate])`, `checkInAt`, optional `checkOutAt`, note, who recorded it). The controller is open to every role (`EVERY_ROLE`) and `PrService` checks `canManagePr` (managers or `managesPr`) for writes and `canViewPr` (plus BOARD) for reads; branch scoping as everywhere. Check-in defaults to now on today's business day; a past day needs `checkInAt` inside that day, never a future day. Deleting a person who was ever called (roll-call entry or room visit) only sets `active=false`. Lists are capped at 500 with `X-Total-Count`. The data purge deletes `PrStaff`, `PrAttendance` and `PrSession` of its scope (and logs `prStaff`, `prAttendances`, `prSessions`).
  `PrSession` is one row per visit of a PR/KTV to an open `Order` (`startAt`, `endAt` null while inside); it is only a time record, never billed (no effect on `billing.ts`, funds or revenue). `PrSessionsService` (`POST /pr/sessions {orderId, prStaffId, startAt?}`, `POST /pr/sessions/:id/end` (no body: ends the visit now, never before `startAt`; a second end is 409 "PR đã ra khỏi phòng"), `PATCH /pr/sessions/:id {startAt?, endAt?}` (corrects the times; `endAt: null` re-opens the visit), `DELETE /pr/sessions/:id`) is open to `canAssignPr` = (`SALES` roles or `managesPr`) and not BOARD (`canManagePr` also excludes BOARD, which stays read-only through `canViewPr`). Every write locks the order first (`lockOrderRow` in `orders/order-lock.ts`, PENDING only), then the `PrStaff` row, and answers with the whole order (`orderDetailInclude`). Rules: a PR has at most one open visit (409 "đang ở phòng …"); the visits of one PR never overlap in time, across rooms (409 "… trùng giờ"; touching visits are fine); `order.startTime ≤ startAt ≤ now` and `startAt ≤ endAt ≤ now`. Checkout and cancelling a session close the open visits at `endTime` (`closeOpenPrSessions`, in the closing transaction). `orderInclude` (lists, the 1000 newest bills) and `orderDetailInclude` (one order, adds `prSessions`) live in `orders/order-include.ts`, so lists do not grow.
  `GET /pr/available` lists the picker (active PR/KTV of the branch, those checked in today first, with the room a PR is in now; cap 500, `X-Total-Count`). `GET /pr/stats?from&to` sums minutes, visits and rooms per PR over business days (a visit counts on the day it started; an open one runs up to now; minutes rounded up per visit) in SQL on `ReportPrismaService`, with `totals` from a second SQL sum; range ≤ 366 days (`businessDatesBetween`); it carries `SharedRequestInterceptor` and `PrViewGuard` (`pr/pr-view.guard.ts`) runs before it, so callers with different rights never share one computation.
- **E-invoices** (`src/einvoice`): see `src/einvoice/CLAUDE.md`.
- **Report site** (`src/report-site`, spec `docs/superpowers/specs/2026-10-02-trang-bao-cao-hddt-design.md`): every route under `/report-site/`, behind `ReportSiteGuard` (`canUseReportSite`; a guard, so it runs before `SharedRequestInterceptor`, whose key ignores the caller), reads on `READERS`, writes on `MANAGERS`. Reads run on `ReportPrismaService` (`bills/summary` and `reports/*` also behind `SharedRequestInterceptor`), except `GET /report-site/manual-bills/:id`, the one read on the main `PrismaService`: its stale-`SENDING` sweep writes, like `GET /einvoices/bill/:orderId`. `POST /auth/login {site: 'report'}` answers 403 "Tài khoản này không được vào trang báo cáo" to an account that may not use the site, after the password and lock checks, so the refused login creates no session or cookie (an early answer only: every route checks). `reportAccess` goes through `reportAccessFor` in `users/users.service.ts` (403 when anyone but the chain manager sends it, 400 when it is turned on for a role other than branch manager/BOARD; a role change clears it there and in `ImportsService`; one log line per change). **Bills thêm tay** (`ManualBill`): `POST /report-site/manual-bills?branch {businessDate (≤ today's business day), roomId (of the branch), amount}` makes the bill and its first draft in one transaction, its number from `nextBillNumberOn` (`orders/bill-number.ts`, the same `BillCounter` statement as checkout, so numbers never clash and the main site's sequence skips them); `POST …/:id/cancel {reason}` locks the bill, deletes its drafts and refuses (409, rolled back) while an invoice is left (sent, uncertain or issued), the number staying used; `GET …/:id` is the panel's detail (`EinvoicesService.manualBillDetail`, as `GET /einvoices/bill/:orderId` is for a paid bill). `GET /report-site/bills` (500, `X-Total-Count`) lists the paid bills holding an e-invoice and the bills thêm tay (Prisma on both tables, merged by business day then sequence), `GET /report-site/bills/summary` the tab counts of every invoice of the branch plus the sums of the days. **Counted e-invoices** (`einvoice-sql.ts` `COUNTED_SQL`/`countedWhere`): every one still there except those not issued of a voided bill, dated by `Einvoice.businessDate`; total = Σ amount, VAT = Σ vatAmount, revenue = total − VAT. `GET /report-site/reports/{revenue,rooms,products}` (`EinvoiceReportsService`, `SharedRequestInterceptor`): revenue by period with comparison and branches, rooms (every room of the scope, "Không phòng"), products from the lines kept in `draft` (`jsonb_array_elements`, grouped by squeezed lower-case name and unit, the first `PRODUCT_ROWS` 1000 then "others", then "Chưa có dòng hàng" so the rows add up). The purge deletes `ManualBill` (after `Einvoice`, before `Room`, logged `manualBills`); a room with a bill thêm tay cannot be deleted.
- Amounts are Prisma `Decimal` (serialized as strings); services convert with `Number(...)` for arithmetic.
